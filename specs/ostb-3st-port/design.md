# OSTB 3ST adaptation

Use a separate ESP-IDF target (`firmware/ostb_3st`) on `codex/ostb-3st-adaptation`. Compile the existing portable GameEngine/scenes/services and data packs. Board-specific code stays under the firmware target; no Arduino, Waveshare BSP, LVGL or Claw dependency is introduced.

The display uses the original device's extracted NV3023 table, 296x240 landscape, MADCTL 0xe8, (24,0) offset and 40MHz SPI. A 142080-byte PSRAM framebuffer owns the native scene. Two internal DMA strips hold 32 rows each. The common RGB565 submission helper also replaces the existing V1/V2 transfer loops, with CO5300 alignment retained in V2. Transfer timeouts require reset before memory reuse.

Display dimensions have 240x135 defaults for existing targets. OSTB overrides them at build time and uses `STICKMON_ROOM_PIXEL_SCALE=1`, matching StickS3. The 480x322 room artwork is sampled down to its 240x161 logical size using the existing StickS3 sampling path. `RoomRenderer::viewport()` centers that rectangle at (28,39), leaving 28 pixels at each side, 39 above and 40 below. `screenX/screenY` add the same destination origin to all world anchors. Because the complete room fits, both camera axes clamp to zero and actor movement does not scroll the background. MainScene world layers are clipped to the room rectangle; background redraw clears the native framebuffer to black so margins cannot stretch or retain stale pixels.

Main/visitor bodies, food, pose offsets, eggs and shadows retain the original 1x StickS3 presentation and frame registration. Body-only float, hop and drop never move ground shadows. The clock and compact per-monster status panels occupy the upper margin, including the two-monster case; tutorial hints and transient notifications use the lower margin. Menus, exploration and battle still use the native full-screen layout. The completed old framebuffer is never scaled. No changes to room simulation coordinates, map generation, pack ids or save schema are required. The previous native-art 2x camera presentation is retained only as historical evidence in the acceptance log.

GPIO40/39 provide active-low A/B. GPIO1 provides the active-high middle key, with internal pulls disabled to match the device's factory firmware. The separate power state machine debounces both edges and requests a shared SaveManager snapshot as soon as a press is stable. This happens before the hardware controller removes supply during a long hold. Short release toggles the screen lock. While locked, the engine suppresses rendering and resets button dispatch; A/B held across unlocking remain blocked until release. A long release after 2s, if the MCU is still powered, requests another save followed by deep sleep with GPIO1 high-level wake; failed persistence cancels that software sleep. Hardware cutoff cannot be cancelled by the firmware. The user confirmed that full power-off and subsequent power-on both require holding the middle key. Factory binary and test evidence are recorded in `hardware-evidence.md`.

Once the power press is debounced and the snapshot committed, the board's main loop polls keys without advancing or drawing the game until release. This keeps the last displayed room position aligned with the early save during the hardware shutdown countdown. Ordinary locked-screen background care resumes after release. Saved world coordinates and the shared format remain unchanged; the native host check restores the actual MainScene and checks its initial position against the snapshot.

The final physical test confirmed the held-key pause and correct position after power-on. The save log at 44871ms and the next captured startup both report room valid=1 and world position (132.00,123.00). This verifies snapshot restoration; software deep-sleep wake remains a separate unverified path.

Original NVS (0x9000, 16KiB) is retained for factory settings and the radio. The game uses a separate 64KiB NVS partition at 0x700000. First provisioning erases only that new partition. Existing bring-up StickMon blobs are imported once, using separate import metadata so a game reset cannot resurrect the old save. No runtime initialization path erases NVS. Resources occupy an 8MiB SPIFFS partition at 0x800000 and are never automatically formatted.

ES8311 speaker playback uses the existing three-channel PcmMixer and the board's I2C/I2S pins. Unavailable acceleration returns false; holding A provides a bath scrub sweep through existing BathInteraction rules. Battery level returns unavailable instead of a fabricated estimate. Microphone, battery calibration and cross-device radio acceptance remain separate hardware work.

## Screen touch extension (2026-10-21)

The user authorized the previously proposed first touch delivery. Probe the reference CST816-compatible device at I2C address 0x15 on SDA12/SCL11, sharing one bus with the audio codec. The input backend reads finger count and raw coordinates every 20ms without adding GPIO guesses or a touch task. Missing hardware leaves A/B usable. A bus error cancels the current contact and requires release before accepting another.

`OstbTouch` performs four-corner affine calibration and an independent center check before enabling game events. The fit accounts for axis exchange, mirrors and scale directly in 296x240 display coordinates; LCD offset24 is not applied to touch. Versioned calibration samples use an explicit little-endian 17-byte blob in the separate `ostb_touch/cal_v1` namespace. Game state and SaveCodec remain unchanged. First startup displays targets, B skips, and A+B held at boot forces setup again.

Setup samples each held contact at the normal 20ms polling rate and uses the median of its latest five coordinates when released. Movement over 15 raw units or holding longer than 1.5 seconds rejects the contact with visible guidance. A failed center check keeps the four fitted corners and asks for another center tap; after three failed center attempts setup restarts at the corners. Fit failure and center retry have explicit on-screen messages. Completing five taps alone does not enable touch; the independent 12px center check must pass.

The optional platform input methods default to no touch for other targets. Portable DOWN/MOVE/UP/CANCEL events pass through GameEngine's lock/fade/resource-alert gates. `Scene` recognizes a single release click on the same target with a 10-pixel movement limit; scenes map it to existing A/B actions or existing menu selection. Main room hitboxes use the same projection and visible-frame registration as drawing. Menu modes and modal targets have distinct identifiers so a release cannot click through a popup. OSTB menu/shop/settings layouts reserve 32 pixels for Back/Select/Confirm; other builds retain their old height. Product taps preview, and a separate confirmation uses the existing shop action.

## Adaptive direct-touch menus (2026-10-21)

The user approved reusing the AMOLED touch-menu style with responsive columns. `MenuGrid` in shared presentation code owns card geometry, gaps, hit tests, scroll limits, labels and main-menu drawing. A minimum card width and font profile determine the column count. AMOLED uses the existing 164x152 two-column profile; OSTB uses a compact profile with three 88x72 cards at 296px width. Both use shared AppSceneFlow entries and MenuAssets. The main grid fills the screen, including its existing Back entry, with no emulated Select/Confirm footer.

OSTB bag and shop use the compact grid below a 38px header. A portable pointer helper provides press feedback and bounded vertical drag scrolling; a drag never becomes a release click. Cancellation is virtual at the Scene boundary so lock, physical input and scene changes clear each scene's pointer state. Grid/detail transitions use separate targets; item taps only enter details. Separate Use/Buy/Sell buttons call the existing gameplay operations. Bag confirmation still gates use; shop action taps buy/sell one unit through existing rules. Other submenus keep the accepted A/B-compatible footer. No changes to gameplay, save layout, resources or the room presentation are required.

## First submenu batch

The approved first batch covers room/food, settings including help/reset, and the computer entry. Shared portable TouchUi controls provide a 38px circular-back header, rows/cards and the AMOLED slider colors. Room has two large cards, food has seven 44px rows with selected/stock indicators, and computer has two destination cards. Manual food scrolling and physical selection reveal share one layout for drawing and hit tests. Contact/communication destination screens keep their existing behavior for the later batch.

Settings presents brightness/volume first, followed by speed/idle/help/reset. It uses a scrolling list and preserves existing setting persistence and audio/brightness APIs. A slider starts only in its track; horizontal movement captures it, vertical movement scrolls without changing the value, and release previews volume once. Lock/physical input/scene switches cancel contacts. Help has previous/next/replay controls; reset uses an isolated confirmation page with Cancel as the safe physical default. Touch-only layouts do not alter StickS3 button rendering, game rules or save schemas.

## Team subtree header and full-width body (2026-10-21)

Requirements 21/22/23 correct the rejected redesign and subsequent narrowed-body version. Only `TouchUi::safeHeaderBounds/safeBack` applies the 28px horizontal corner clearance, with the Back target at (28,4,40,40). `TouchUi::pageBody` is independently (0,48,296,176): the 4px top margin reduces header height to 48px and moves the body up 12px while keeping its bottom at y=224 and full native width. Team cards use ordinary 8px side margins and are 280x76; action popups use the normal right margin. Body rendering, hit tests, list reveal and gestures share the full-width geometry. The header safety check applies only above the body, so it cannot disable content near either side.

The original status and moves renderers retain their content positions and pixel sizes. Status keeps its five-page field/stat order and page dots, horizontal swipes/header-title paging and vertical overflow dragging. Moves keeps the 90px left list, 24px rows, x=97 details, original fields/bar, horizontal description marquee and compact 190x72 default-No confirmation. A row tap selects/inspects; tapping the current row invokes the existing A action. Explicit Back rows and the header unwind the existing navigation. No bottom Select/Confirm or Previous/Next strip is drawn or hit-tested.

Static status pages park; only the original overflowing move-description marquee and toast expiry request updates. Non-touch coordinates and game/save rules are unchanged. Host checks compare full-width original stat/EV/IV/moves pixels except the separately centered status dots, and exercise both card edges, left-edge move input and status swipes, protected header corners, modal isolation and actual forget/recall effects. Rounded-mask previews and firmware builds supplement physical acceptance. Other page groups remain deferred; R56 is an unmeasured preview estimate and does not constrain body width.

## Status indicator and home battery (2026-10-21)

Horizontal paging and vertical overflow dragging remain unchanged. The touch status indicator is rendered after the body clip is removed: a centered 52x16 dark pill at (122,216) contains five 4x4 dots starting at (130,222), with 8px pitch. It overlays the content and consumes no layout space or action target. Non-touch indicators retain their original side placement.

`HudRenderer::drawBattery` now owns the original AMOLED 36x16 battery outline/fill/unknown dash, shared by AMOLED HomeScreen and OSTB MainScene. OSTB's top clock panel is (172,12,96,22), clock at (180,15), battery at (226,15). It fits beside two existing member panels and above the unchanged room. The hardware API caches the averaged/smoothed factory ADC curve estimate for ten seconds; rendering never performs an ADC read on every frame. Failed samples invalidate the estimate and render the unknown dash until recovery.
