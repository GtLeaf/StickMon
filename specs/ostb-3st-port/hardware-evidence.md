# Device-specific middle key

The original 2.2.2 firmware from this device differs from the public 3ST reference, which defines BOOT as GPIO0. The original flash backup remains private outside Git. Its SHA256 is `8e07cf9f43cb8750b9cef8175806adbf90ded420ac8d4320f719da05fdaf280e`.

The OTA0 image at flash offset 0x20000 maps its instruction segment at 0x42000020. In the `OSTB_XIAOZHI_3ST` board constructor at 0x420259a0, three calls to the same `Button` constructor at 0x4202231c use these arguments:

| Call address | Object offset | GPIO | active_high |
| --- | --- | --- | --- |
| 0x420259d2 | 48 | 1 | true |
| 0x420259ee | 152 | 40 | false |
| 0x42025a07 | 256 | 39 | false |

The constructor's error message identifies its signature as `Button::Button(gpio_num_t, bool, uint16_t, uint16_t, bool)`. The public [Button implementation](https://github.com/78/xiaozhi-esp32/blob/main/main/boards/common/button.cc) names the second parameter `active_high`. The two active-low inputs match the independently verified physical A/B buttons.

The factory constructor also treats GPIO1 specially: at 0x4202239b it tests `gpio_num == 1`, then at 0x4202239e writes 1 into GPIO config byte 6. This is the `disable_pull` field in [button_gpio_config_t](https://github.com/espressif/esp-iot-solution/blob/master/components/button/include/button_gpio.h). The GPIO driver checks byte 6 at 0x420be950 and skips configuring either internal pull when it is set. The new target therefore configures GPIO1 as input with both pulls disabled and treats level 1 as pressed.

During bring-up, a temporary diagnostic build enabled pull-ups on several unused candidate pins, including GPIO1. The device disconnected during that experiment. The probe was removed and the stable game restored before using the recovered mapping. No other candidate pins are configured for probing in the delivered target.

The app-only restore was verified on hardware: 8MiB PSRAM passed the startup memory test, the game rendered, and `saved snapshot readable=1, hatched=1` confirmed the existing save survived the update and reset. The user confirmed middle-key lock/unlock on the corrected build. Logs show GPIO1 rising/falling for both presses, followed by `Screen locked` and `Screen unlocked`.

During the long-press test, GPIO1 rose and a brownout was reported before any release or software deep-sleep action. The user confirmed long press powers off, short press cannot restart from full power-off, and long press starts the device again. This is consistent with direct control by a hardware power controller. The implementation therefore requests persistence on the debounced press, before supply can be removed; waiting for release would be too late. It retains software deep sleep on a long release only as a fallback if supply remains present. That fallback and its wake path are not hardware accepted.

The following physical cycle verified the early save: GPIO1 rose at 57379ms, `Power key snapshot saved before hardware cutoff` was logged at 57640ms, and the next startup reported a readable hatched snapshot. The user confirmed the same monster survived power-off/on, but noticed its position changed. The early save previously allowed the monster to keep moving during the remaining hold; the native host check confirms that MainScene can restore the exact saved world coordinates. The final board loop pauses game updates/rendering while the debounced power key is held, so the visible position stays aligned with that snapshot.

The final device check passed on 2026-10-21. The user confirmed that holding the middle key pauses the game and that power-on restores the correct position. Firmware ELF SHA256 prefix `0adf7180e` logged GPIO1 high at 44610ms and a successful snapshot at 44871ms, with `room=1 position=(132.00,123.00)`. The next captured startup reported `saved snapshot readable=1, hatched=1; room=1 position=(132.00,123.00)`. Here `room=1` means the room snapshot is valid. Normal movement resumes after startup. The captured reset reason was `USB_UART_CHIP_RESET` after serial reconnection, so these logs support persistence and position restoration, not software deep-sleep wake acceptance.

## Startup display sequencing

The user subsequently reported garbage pixels before the game appeared on each power-on. Code inspection found that `GameEngine::begin()` loads the saved brightness before any rendered frame is submitted. `OstbPlatform::setBrightness()` immediately applied it, while the panel init table had already sent display-on (0x29) without uploading valid pixel data. The black, zeroed PSRAM framebuffer alone did not initialize the panel RAM.

The corrected board code drives GPIO13 low before storage initialization, starts PWM at duty zero, and defers 0x29 and the table's empty RAM-write command. All brightness changes remain gated until the first full-frame transfer completes. Only then does the board send display-on, wait the original 10ms delay, and apply the saved brightness. No claim is made about the backlight's electrical state before application startup.

The OSTB build passed and the app-only update was hash-verified on 2026-10-21. Firmware ELF SHA256 prefix `f458c8685` booted successfully, loaded the existing hatched snapshot at 2140ms and logged `First complete frame ready; enabling display backlight` at 2675ms. The initial present took 41.3ms including the deferred display-on delay; later full-frame transfers remain about 30.6ms. The user then performed a long-press power-off/on cycle and confirmed that startup garbage disappeared: the screen remains black briefly, then shows the normal game. The startup sequencing fix is physically accepted on this device.
