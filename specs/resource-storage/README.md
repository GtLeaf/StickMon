# 独立资源文件系统与分区方案

更新：2026-11-09。谷仓默认 16 MiB 地址范围／9 MiB 共享资源区，可显式选择完整 32 MiB／24 MiB 资源；首版完整安装，应用内 USB 资源更新明确关闭。微雪／StickS3 部分仍为设计。

目标：精灵、地图、音频、字体、家具、对白及内容数据表从应用镜像移出，
应用保留玩法引擎、表现逻辑、硬件适配和更新／恢复能力。主推微雪 16 MiB
与独立谷仓 32 MiB；StickS3 8 MiB 沿用现有布局并共享读取接口。
Claw、OSTB 暂不纳入本轮迁移。

当前仅落地谷仓，具体实现、安装事务和验收以
[谷仓 32 MiB 细化方案](sdgoods.md)为准；微雪／StickS3 分区迁移暂不推进。

本目录两份 CSV 仅为方案快照，不被构建引用。谷仓实际使用
`firmware/sdgoods/partitions.csv`；其他目标分区不变。
文中容量均为二进制 MiB（1 MiB = 1,048,576 B），结束地址为不包含的边界。

## 1. 当前状况

| 目标 | 当前资源方式 | 尚未达到目标的部分 |
| --- | --- | --- |
| StickS3，8 MiB | 独立 LittleFS，资源区 3.625 MiB | 精灵／技能内容表、地图布局等仍编入应用 |
| 微雪 V1／V2，16 MiB | 独立 4 MiB SPIFFS，图片、动画、音频已外置 | 内容表和地图布局仍内嵌；剩余高地址被 5.8125 MiB `brainfs` 等分区占用 |
| 谷仓，32 MiB | 自有双 OTA＋单个 9 MiB 只读 LittleFS；49 张内容表外置，完整安装实现 | 首版完整安装；运行中资源更新关闭，资源断电恢复需后续原子 staging 设计 |

微雪导出文件名 `littlefs.bin` 并不代表实际使用 LittleFS：当前挂载走
`esp_vfs_spiffs_register`，镜像由 `spiffs_create_partition_image` 生成。
SPIFFS 不能靠改文件名或分区 subtype 原地变成 LittleFS。

谷仓每个应用槽仍为 3 MiB，外置后的当前 Release 为 1,316,800 B；
这不是整片 Flash 的容量或硬件上限。以下原状与容量快照保留为设计依据。
本方案使用项目自有的独立固件分区表，不沿用 SDK 的 factory launcher／动态多应用布局。
已测设备低地址为两个 3 MiB OTA 槽及 `resources` 0x620000／4 MiB；
实施前仍需核对完整实际分区，不能用 SDK 表或旧日志推断整片布局。

## 2. 推荐分区

### 微雪 V1／V2：16 MiB，单资源区优先容量

V1／V2 共用存储布局和资源格式，面板、触摸驱动与校准仍按硬件区分。

| 分区 | 起始地址 | 大小 | 结束地址 | 用途 |
| --- | --- | --- | --- | --- |
| 启动及低地址预留 | 0x000000 | 128 KiB | 0x020000 | 包含下述 NVS／OTA 元数据／PHY，勿重复计数 |
| `ota_0` | 0x020000 | 3 MiB | 0x320000 | 玩法应用 A |
| `ota_1` | 0x320000 | 3 MiB | 0x620000 | 玩法应用 B／回退 |
| `resources` | 0x620000 | **9 MiB** | 0xF20000 | LittleFS，资源与不可变版本目录 |
| `userdata` | 0xF20000 | 768 KiB | 0xFE0000 | LittleFS，未来用户文件／自定义房间等 |
| `resmeta` | 0xFE0000 | 64 KiB | 0xFF0000 | NVS，应用槽与资源版本绑定、升级事务状态 |
| `coredump` | 0xFF0000 | 64 KiB | 0x1000000 | 崩溃转储，需实测配置能容纳 |

低地址维持 `nvs` 0x9000／0x6000、`otadata` 0xF000／0x2000、
`phy_init` 0x11000／0x1000，余下空间为启动层和应用对齐预留。
16 MiB 已全部规划；不额外保留暂停迭代的 Claw `brainfs`。

9 MiB 是物理分区，不承诺能装满 9 MiB 文件。初期以资源／版本共用后总占用不超过
约 80% 为容量目标，最终按打包器与文件系统实测设限。满量更新还须留旧新版本并存空间。

不首选两个 4.5 MiB 资源区：其单份相对当前约 3.2 MiB 载荷增长余量有限，
再外置地图布局和数据表后更紧张。若未来优先要求任意整包更新都能回退，
可改选这一折中，但会牺牲可用内容容量，不能同时宣称有 9 MiB 活跃资源容量。

候选表：[partitions-16m-proposal.csv](partitions-16m-proposal.csv)。

### 独立谷仓：物理 32 MiB，整张分区表限制为 16 MiB

| 分区 | 起始地址 | 大小 | 结束地址 | 用途 |
| --- | --- | --- | --- | --- |
| 启动及低地址预留 | 0x000000 | 128 KiB | 0x020000 | 同微雪的低地址规划，实际迁移前核对 |
| `ota_0` | 0x020000 | 3 MiB | 0x320000 | 玩法应用 A |
| `ota_1` | 0x320000 | 3 MiB | 0x620000 | 玩法应用 B |
| `resources` | 0x620000 | **9 MiB** | 0xF20000 | LittleFS，两个 OTA 应用共享的资源 |
| `userdata` | 0xF20000 | 768 KiB | 0xFE0000 | LittleFS，用户文件 |
| `resmeta` | 0xFE0000 | 64 KiB | 0xFF0000 | NVS，配对／事务元数据 |
| `coredump` | 0xFF0000 | 64 KiB | 0x1000000 | 崩溃转储 |

地址范围到 0x1000000，共 16 MiB；高地址 16 MiB 暂不分区，默认布局与微雪的 16 MiB 规划对齐。共享资源区容量为 **9 MiB**，两个 OTA 应用槽共用同一份资源镜像；不再重复保留 A/B 资源。资源区建议保留约 20% 空闲。
两个应用槽各 3 MiB 是有意给玩法框架设置的预算，资源移出后重新测量 Debug／Release
镜像大小；不以当前带内嵌资源的谷仓应用接近 3 MiB 推断移出后的框架仍然超限。

默认几何：[partitions-16m-proposal.csv](partitions-16m-proposal.csv)；完整 32 MiB 快照：[partitions-32m-proposal.csv](partitions-32m-proposal.csv)；
实际表：`firmware/sdgoods/partitions.csv`。
谷仓专属实施设计见[谷仓 32 MiB 细化方案](sdgoods.md)。

### StickS3：8 MiB，兼容现有布局

保留 `partitions_stickmon_8mb.csv`：两个 2.125 MiB 应用槽、3.625 MiB LittleFS、
NVS／OTA 元数据及 64 KiB coredump。共享资源目录和数据格式，按设备 profile
裁选 UI／字体，不复制微雪／谷仓整包。先测真实资源占用再决定是否需要精简音频；
当前方案不承诺 8 MiB 设备能容纳后续所有大容量内容。
无新增 `resmeta` 分区时，可在现有 NVS 专用命名空间存绑定记录，先验证容量。

## 3. 文件与代码边界

统一使用 LittleFS；`ResourcePack`／`ResourceFS`／`Platform::IResourceStore`
继续作为共享入口，各端只实现挂载、读写和容量报告。资源区平时只读，只有更新服务
取得写权限；用户文件使用独立挂载点，刷资源不触及用户文件。

| 进入资源文件系统 | 保留在固件 |
| --- | --- |
| 精灵图片、方向／动画索引、叫声、显示尺寸与锚点 | 精灵动画播放器、缓存和绘制器 |
| 图块、地图图层、碰撞／道路／NPC 点位、地图生成配方 | 地图生成算法、寻路、遮挡与地图会话 |
| 属性种族值、进化条件、学习表、招式数值／描述、遭遇与掉落表 | 战斗／成长／进化／掉落规则执行器及已支持的效果处理 |
| 音乐／音效、字体、家具外观／目录、对白、商品目录 | 音频解码、UI 状态机、交易／存档事务和硬件服务 |

例如 `Species.cpp`、`OfficialMoveData.inc`、`MarketMapData.h` 与各
`Explore*Data.h` 中的内容数据逐批转为版本化二进制；生成算法本身保留。
不把原始编辑器 JSON、原图或 WAV 整套放设备上：开发源继续在 `origin_asset/`，
生成器输出有边界检查、显式字节序和校验的设备格式。编辑器应增加设备二进制导出，
避免继续把地图 C++ 头文件作为唯一运行时产物。

目标逻辑目录为 `sprites/`、`cries/`、`audio/`、`fonts/`、`game/`、`rooms/`、
`maps/`、`catalog/`、`text/`；`origin_asset` 与大体积原始源不随发布包安装。
16 MiB 物理层可存 `/blobs/<sha256>` 与 `/generations/<id>/catalog.bin`，
目录项将逻辑路径映射到不可变 blob；谷仓 32 MiB 共享资源区含完整的一套目录。
共享读取器解析逻辑路径，不要求玩法代码感知资源镜像或 blob。

物种、招式、道具、地图使用稳定 ID，存档不能持久化数组位置或资源指针。
现有 `GameAssets::Kind` 和生成顺序先保持不变，再通过版本化 registry 解耦，
不能直接重排已有枚举。资源解析需限制文件长、索引数、地图尺寸和解压目标内存，
未知效果 ID／不支持的内容 schema 拒绝激活。资源更新能增加已支持规则下的内容，
新增战斗机制或超出固件上限仍需更新应用。

固件仅内置最小故障提示字体、恢复页面和 USB 修复能力，避免资源丢失后黑屏且
无法恢复；不保留整套精灵／地图作为 fallback。外置不等于不占 RAM：音频继续流式，
图块／精灵按场景缓存，不在每帧重新读目录或解码整包。

## 4. 版本、更新与回退

发布 manifest 至少包含 `layout_id`、硬件 profile、应用版本／hash、资源 generation／hash、
资源 schema、content ABI、各文件长度／hash 与容量需求；发布签名覆盖应用和共享资源镜像。
ABI 表示 ID／效果语义和解析契约，不能仅用“资源版本号更大”判断兼容。
绑定记录同时包含应用镜像 hash，避免槽位重用后沿用错误资源。

### 16 MiB：文件级增量与不可变 generation

1. 预检新应用与资源兼容、签名和容量。按旧／新／仍需回退版本的 blob 并集计算空间，
   加上 LittleFS 元数据与空闲余量；不能只看下载增量大小。
2. 写入缺失 blob，关闭／同步文件，核对长度与 hash；已被有效版本引用的文件不覆盖。
3. 写入并校验新 catalog。资源不完整时不产生已提交 generation。
4. 写备用应用槽，校验后以带 sequence／CRC 的双记录保存该应用 hash→generation 绑定。
   保持当前应用绑定有效，最后才设置 OTA 下次启动槽。
5. 新应用启动时验证绑定、核心目录和存档可读，再标记应用有效。失败回到旧应用及其
   原 generation；不能依赖全局 `/active.json` 自动替所有应用切换。
6. GC 只删除当前应用、有效回退应用及待提交事务均不可达的 blob。重用备用应用槽前，
   明确释放被替换旧应用的 pin；事务未提交前当前应用及资源始终保留。

资源单独升级第一版暂不开放，统一走应用＋资源配对发布，先减少状态组合。
后续开放时必须满足双方 ABI 和保存格式兼容，单独设计资源回退事务。

单资源区不能保证在任意占用率下同时容纳两份完全不同的整包；不足时拒绝在线更新，
不能删除当前版本来硬凑空间。USB 维护模式允许重装完整资源镜像，但过程中的断电可能
需要再次安装。**禁止在正常运行中原始覆盖当前挂载的 LittleFS 镜像。**

### 32 MiB：双 OTA 应用共享资源

两个 OTA 应用槽共享 `resources`；应用与资源统一通过完整安装交付，运行中不覆盖当前挂载资源。
完整安装器先校验 9 MiB 资源镜像、应用和绑定，再写入固定地址并设置下次启动应用。
资源或分区表变化时断电需要重新执行安装器；首版不提供运行中资源更新或资源 A/B 回退。

ESP-IDF 的应用 OTA／rollback 不会自动替应用回退自定义资源选择状态；
`resmeta`、启动检查、绑定校验和掉电恢复需要项目实现。启用并验证 bootloader rollback，
不能只因为分区表有两个 OTA 槽就宣称已经具备回退能力。

### 存档独立于资源回退

原 NVS 内保存的存档、设置、触摸校准继续保留，第一阶段不切换保存后端。
`userdata` 先预留给后续用户文件；若迁移存档，必须复用共享 SaveCodec，成功写入
并验证新副本后才能认定迁移完成。不能格式化 NVS，也不能因资源错误重置游戏。

回退旧应用还要求其能读新应用写出的存档。涉及不向后兼容的保存 schema 时，
必须在试运行期间延后不可逆迁移，或另行设计版本化存档副本及回退规则；
仅保留两份应用与资源不代表保存状态也能自动回退。遇更新版本档继续写保护。

## 5. 总体顺序与迁移边界（谷仓已先完成三批实现）

1. **统一契约与测量**：确定 layout ID、稳定内容 ID／ABI、manifest 和读取接口，
   记录各目标 app／资源实际大小与解码内存预算；建立候选布局容量检查。
2. **谷仓先移出内嵌资源**：以项目自有表构建 LittleFS，移除 bulk archive 的
   `target_add_binary_data`；合并目前的外置音频层，验证音频／图片同一入口。
3. **微雪统一 LittleFS**：V1／V2 同时切换挂载与生成镜像，保留各自驱动和校准；
   暂停使用的 `brainfs` 空间转入新资源区。Stick 继续兼容其现有 LittleFS。
4. **外置内容表与地图**：先精灵／技能目录，再地图布局／生成配方／NPC 与遭遇配置；
   每批对照原数据和实际游戏结果，保持随机调用顺序、ID 及存档语义。
5. **升级事务与实机验证**：接入 16 MiB generation、32 MiB 完整安装和回退验证，
   再开放资源随版本分发。当前只提供明确的 USB 完整安装流程。

现有 V2 OTA 是应用更新，且 `OtaRuntime::layoutHealthy()` 写死 4 MiB SPIFFS 布局，
资源 hash 也和构建版本绑定；不能用它直接升级到本方案。首次切换走一次 USB 维护迁移，
配套更新 bootloader（若所需）、分区表、应用、资源和发布／刷机工具；
刷机偏移从目标布局生成，拒绝混用旧 `flash_args` 或不同 build 的镜像。
导出名统一 `resources.bin`，镜像类型／布局版本由 manifest 明确标记。

迁移先核对设备容量、完整实际分区、应用槽和保存位置，遵守不自动备份的用户约定，
定点写入并验证，保留原 NVS／校准。不得整片 erase，也不能沿用会覆盖完整 NVS 的
旧 Claw 初始化脚本。原 `brainfs` 与旧高地址 coredump 被重新划分，不能承诺其内容保留；
有仍需使用的文件时先设计迁出。新旧资源格式不同，必须重建资源镜像。

改写分区表本身不是普通双槽 OTA 的掉电安全操作，首次迁移与后续更新安全边界不同。
即便保持应用起始地址不变，旧固件仍可能依赖 SPIFFS、旧长度或旧资源，
不能把新分区表与任意旧应用组合启动。当前临近发布版本可继续现有布局，
本方案单独作为一次存储升级交付。

## 6. 验收条件

- CSV 无重叠、满足对齐、各条目不越过物理容量；16／32 MiB 顶部地址与预期相同。
- 所有目标从资源文件读取相同逻辑目录；谷仓 app 不再内嵌 bulk 资源，实际容量报告准确。
- 新增一个使用现有效果的精灵／一张现有规则地图无需重编内容表进 app；不要求支持新机制。
- 文件缺失、坏索引、短读、错误 schema／ABI、空间不足均拒绝激活，原资源和存档不被覆盖。
- 更新每个关键提交点断电重启，启动的应用与资源 generation 始终匹配；资源错误可进入恢复页。
- 新旧存档读写／版本保护、V1／V2 独立校准、字体、音效、叫声和地图／战斗结果回归。
- 各目标真实构建与设备验证分别记录；主机测试不代替真机音频、读盘延迟、FPS 和掉电测试。

本轮仅设计及候选 CSV 几何校验，以上运行时、迁移与设备验收均待实现。
2026-11-05 已通过 ESP-IDF 5.5.4 分区生成器的容量／字段校验、二进制往返解析及
独立对齐／无重叠检查；16 MiB／32 MiB 末端分别为 0x1000000／0xF00000。
本地记录：`.stick-local/artifacts/resource-partition-design-20261105/verification.json`。
未构建固件、访问串口或刷机。
