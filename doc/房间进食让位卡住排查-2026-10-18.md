# 房间进食后让位卡住

日期：2026-10-18。已在连接的微雪 V2 和原生真实应用中复现并修复。

## 复现与原因

实机连续日志显示，第一只奇鲁莉安饱腹为 0，位置为 `(118,119)`；第二只卡咪龟饱腹为 87，仍在碗边 `(65,122)`。碗中还有一份普通粮、3 口。两只均健康、清醒且允许自动活动。

食盆没有持有者，第一只被碗边阻挡检查拒绝领取，第二只反复尝试让位。原让位选点仅检查距离进食点 40、52、64 的固定圆环；本场景这些落点与等待的精灵重叠，或超出实际可走区域。实际只需走到 `(89,116)` 就能让开，但原搜索跳过了这一距离，形成持续等待。实机观察 25 秒、原生应用推进 60 秒，位置均没有恢复。

## 修复

`AmoledApp::startCompanionFoodExit` 先尝试双方足迹决定的让位距离加 2、加 8，再尝试原有远点；继续通过既有足迹、碰撞和寻路检查。本例的让位距离为 30，新增的 32 距离落点可达。无需调整存档或进食数值。

新增真实应用回归，使用上述精灵、坐标和房间资源，覆盖：

- 恢复已卡住的状态：饱腹 87 的伙伴让位，饱腹 0 的主精灵取得食盆、吃到 75 并结束让位会话。
- 两只都饥饿：通过真实食盆触摸补粮，伙伴先吃完并离开，再补第二份，主精灵吃完并离开。
- 连续过程中检查资源归属、任务不变量，以及局部刷新与完整画面的像素一致性。

修复前新增用例失败，修复后通过；关闭 Debug 的配置也通过该用例。Debug 原生应用 59 项、房间行为 29 项、房间运行时 7 项通过，不累计重叠检查。V1/V2 各 lite、lite debug 及 AMOLED V2 Web 共 5 个构建通过；263 项生产输入哈希保持一致。

## 实机结果

备份原 NVS 后，刷入同一 V2 lite debug 构建的五份镜像，写入校验全部通过。直接加载原卡住存档，未使用测试精灵替换队伍：

- 卡咪龟从 `(65,122)` 向 `(89,116)` 让位。
- 奇鲁莉安随后走到食盆，饱腹依次 `0→25→50→75`，每口只结算一次。
- 碗清空，进食及让位会话结束，两只继续活动；持续记录 60 秒，未见崩溃或看门狗异常。
- 再次重启后，正常读取饱腹 `75/87`、空碗，原队伍、金币、等级及背包诊断值保留。此次食物与照料收益按正常玩法保存。

日志位于 `tools/out/home-food-stall-20261018/`：`device-stalled.log` 为修复前，`device-fixed.log` 为修复后，`device-reboot.log` 为重启复核；12 项实机日志检查全部通过，结果见 `device-results.json`。设备保留修复后的 V2 lite debug 版本。本次硬件验证范围为该设备上的房间流程。
