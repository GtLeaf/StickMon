# StickMon 代码结构风险与重构方案

日期：2026-10-18。基于当前工作区源码，包括尚未提交的开发内容；初始阶段为结构分析；用户确认后的首批实施结果见第 8 节。

## 1. 结论与目标

建议采用“先补保存可靠性缺口，再逐个迁移状态所有权”的渐进重构。

当前范围调整：Claw 暂停迭代，其专项修复移入后续待办，不作为 AmoledApp 拆分的前置条件。保留现有功能与 HostAdapter 接口；拆分触及其调用路径时，只做必要的兼容迁移与回归验证。暂停迭代不代表禁用现有运行入口，也不表示已记录的风险消失。

`AmoledApp` 的问题不只是行数多，而是输入、页面流程、玩法调用、动画时序、硬件副作用和持久化聚集在一个对象中。只拆成多个实现同一类的 `.cpp`，或继续增加 `.inc`，无法降低耦合。每次拆分应同时迁走对应的状态、转换逻辑和测试。

项目已有较好的共享基础：纯玩法服务、Home::Simulation、独立页面 Controller、显式存档编码与 A/B 校验、渲染缓存所有权、跨目标源码清单。应继续完成这些边界，避免重建一套框架。

目标是让一个页面或流程的修改只影响其所属模块，并能独立验证；同时保留三种硬件目标和 Web 模拟器的规则、存档与资源兼容性。

## 2. 当前结构

```text
StickS3: GameEngine -> src/scenes/* -------------------+
                                                     +-> src/game/* 共享规则
AMOLED V1/V2/Web: AmoledApp -> HomeScreen / ui/* -------+
       |               |
       +-> app/*       +-> presentation/* / RenderCaches
       +-> SaveManager / GameClockService / VisitSessionService
       +-> PlatformServices -> 各平台适配
       +-> BrainBridge / Claw（AMOLED 可选）
```

| 模块 | 当前规模 | 结构观察 |
| --- | ---: | --- |
| AmoledApp.cpp / .h | 约 14,842 / 986 行 | 约 280 个方法；持有几乎所有 AMOLED 流程状态 |
| handleTap / handleTouch | 约 1,018 / 672 行 | 多页面点击、拖动、取消和弹窗仲裁集中分支 |
| update / render | 约 623 / 531 行 | 同一页面的知识在输入、更新、绘制等入口反复出现 |
| updatePet / updateExploreDeparture | 约 716 / 646 行 | 房间行为、出发流程与表现状态交错 |
| HomeScreen.cpp | 3,980 行 | 另文本包含四个页面 .inc；分文件但仍共用编译单元内部上下文 |
| MainScene / ExploreScene / MenuScene | 7,710 / 5,158 / 3,205 行 | StickS3 也存在大场景类，需同步控制规则继续向场景聚集 |
| GameEngine.cpp | 2,703 行 | 引擎协调之外，还包括拜访、联系人、探索和调试流程 |
| V1 / V2 main.cpp | 1,188 / 1,383 行 | 显示循环、锁屏、电源、传屏协调有较多相似代码 |

行数包含空行、注释和条件编译分支，仅用于定位责任聚集，不代表运行时内存或性能。统计排除了构建产物与 tools/out 的历史副本。

## 3. 风险与证据

优先级含义：P1 为优先解决的可靠性问题或高影响耦合；P2 为渐进治理项。下述静态竞态分析不等于已经在实机复现。

### R1 / P1：保存失败后的补偿机制在两套应用间不一致

证据：`AmoledApp.cpp:7338–7385` 的周期保存调用 `saveState()` 后，无论成功与否都更新 `lastPersistMs`；周期为五分钟，探索会话和战斗期间还会跳过这一周期路径。许多奖励、购买等调用也没有处理保存失败。

影响：写入失败后，最新状态继续留在 RAM；若没有其他保存触发，周期补偿至少延后到下一周期，掉电可能丢失最近进度。这是持久化及时性问题，并不表示 A/B 存档会直接损坏。

已有保护：`SaveManager` / `SaveCodec` 已有 A/B、CRC、迁移和高版本写保护；孵化完成先提交快照再清理蛋进度，洗澡也有单独重试路径，应保留。

建议：复用 [SaveCoordinator](../src/core/SaveCoordinator.h)，它已经被 StickS3 的 `GameEngine` 使用。AMOLED 接入统一的 dirty、延期、尽快保存与失败重试调度；将房间视图快照转换独立为 SnapshotBuilder，存储仍由 SaveManager 完成。普通合并写与关键提交须区分，不能让孵化完成等关键步骤变成异步“尽力保存”。

快照与遭遇历史目前分别提交。应记录各自结果并明确补偿策略，不必为非关键历史数据强行引入新的跨 blob 事务或更改 schema。

### R2 / P1（延期，Claw 恢复迭代时处理）：超时重试的安全承诺不成立，队列存在竞态窗口

证据：`BrainBridge.cpp:95` 附近注释称 host 回调重试安全，但 `AmoledApp::brainBuyFood()`（约 2192 行）每次调用 `ShopService::buy()` 都可能再次扣币、增加库存；`brainEat()` 也可能继续消耗食物。Request 有 `requestId`，但 BrainBridge 没有使用它去重。

队列的另一处静态风险：`BrainBridge.cpp:207–235` 完成执行后把 `processing` 设回 false，等待线程消费前仍可能保持 `inUse=true`。下一次 update 可以再次认领该槽。超时释放槽与临界区外的 semaphore give 之间，也存在槽复用后接收旧通知的窗口。

影响：超时并不代表未执行；重试可能重复购买或消耗。具体发生概率取决于任务调度，需要确定性时序测试和实机验证。

后续修复建议：独立于主线结构重构处理。明确 FREE / QUEUED / EXECUTING / COMPLETED 状态，完成态不可再次执行；通知与槽复用使用代次校验或不复用的完成通道。超时区分“尚未执行并取消”和“执行中、结果待确认”。近期保留风险记录，不要求先完成该修复才能拆分 App。

幂等键必须标识一次工具调用，不能直接假定已有 requestId 唯一：同一 LLM 请求可能包含多次合法购买。核查上游 ID 语义，采用会话 + 工具调用 ID，配合固定容量结果缓存。若上游不能保留相同调用 ID，至少不能把未知执行结果自动重试解释为安全。

### R3 / P1：状态所有权不完整，容易出现合法字段组成非法状态

证据：`AmoledApp.h:770–850` 同时持有战斗阶段、continuation、换人阶段及大量动画、音效、日志、胜利结算布尔状态。`handleTouch`、`handleTap`、`update`、`render` 都需要理解这些组合。

Team、Inventory、Shower、Hatch Controller 已抽出，但仍暴露可写 `State& state()`，App 在外部修改其字段；[app/README](../firmware/amoled_1_8_v1/main/app/README.md) 也明确这是过渡接口。

影响：退出页面可能漏清某个状态；取消手势、战斗结算、升级后返回、锁屏恢复等跨流程路径容易回归。当前已有 enum，并非完全没有状态机，问题是约束分散。

建议：Controller 提供完整操作，例如 beginGesture / cancelGesture / open / close / acceptFeedback；只公开 const 状态与 ViewModel。BattleSession 持有战斗流程状态，BattleTimeline 持有音画时间线。互斥阶段使用 enum；真正并行的动画保留独立子状态，不强行塞进一个巨大 enum。

### R4 / P1：场景切换和传屏确认具有隐藏时序契约

证据：`markRendered()`（约 11942 行）不仅清理脏区，还确认淡入淡出帧已呈现，并放行战斗音效。`AppSceneFlow::Controller::enter()` 本身只是设置语义场景，不负责取消手势、暂停时钟、停止 IMU 或释放会话资源。

影响：抽类时若把这些动作顺序改变，可能出现黑帧、音效提前、旧页面 release 触发新页面按钮、缓存过早释放或静止页持续刷新。

建议：先记录并验证输入 -> 更新 -> 构建模型 -> 绘制/传屏 -> 呈现确认的契约。引入薄的页面生命周期接口，逐页统一 exit/cancel、enter、present acknowledgement；锁屏、省电及亮度淡变沿用当前已验证的特殊处理，不能假定每次确认都对应一次物理 LCD 传输。

### R5 / P2：两套 UI 都有大型适配流程，规则继续分叉的风险较高

证据：StickS3 的 MainScene、ExploreScene 与 AMOLED App 均持有大量房间、探索和成长协调。共享 Home::Simulation、ActorController、BattleActionService、BattleTurnController 等已经存在，但平台场景仍有很厚的规则调用与表现胶水。

影响：只给 AMOLED 修复奖励、访客、切换队伍等流程，可能遗漏 StickS3 的同等行为；直接复制新代码会扩大维护成本。

建议：区分“玩法规则”和“竖屏交互”。纯状态变更与资格判定进 src/game；跨平台会话协调进入 src/core；触摸惯性、布局、动画进 AMOLED app/ui。优先对同一操作建立跨适配器的 GameState 结果验证，不要求横屏和竖屏共用输入状态机。

### R6 / P2：测试部分绑定源码位置，安全抽取也会触发失败

证据：[test_architecture_boundaries.py](../tools/test_architecture_boundaries.py) 一部分测试检查具体函数调用、字段名必须出现在 AmoledApp.cpp 或 MainScene.cpp。正确移入新文件后仍可能失败；App 还有多处 friend 测试入口。

建议：保留 SDK/依赖方向的静态检查，将检查范围扩展到清单包含的模块；行为保证用固定时间、随机数和输入序列验证。已有公开 touch/update/render 页面测试可直接复用，避免重写测试体系。私有状态访问按迁移逐步缩小，不一次删除全部测试入口。

### R7 / P2：UI 和板级实现的物理边界仍不清晰

HomeScreen 文本包含 TeamScreens、ItemShopScreens、ComputerScreens、ExploreScreens，文件之间仍隐式共享 helper 和上下文。V2/Web 又依赖名为 V1 的目录，板级启动和显示循环存在相似实现。

建议：先让页面 renderer 成为独立 .cpp，显式依赖 UiCommon、布局和 ViewModel；生命周期明确后，再提取公共 AMOLED runtime 与各板 BSP hooks。最后单独提交目录迁移。源码清单已经统一，不应再维护多套列表，也不应把目录搬迁和行为改动混在一起。

### R8 / P2：资源与内存需要预算管理，拆文件不会自动省内存

现有 RenderCaches 已有 RAII、场景保留策略与分配失败路径，不能据此报告“缓存全部泄漏”。V1/V2 的 App 也已经是 static 对象，不存在从大类行数直接推导出的当前栈溢出；头文件里“App 在 app_main 栈上”的旧注释需要修正。

风险在于重构若复制大型状态、缓存、ViewModel，或引入动态事件总线，会增加常驻内存和堆碎片。当前分区布局已覆盖 16 MB 地址范围，应用 OTA 槽各 3 MB；实际应用余量要看各配置产物，不能把“分区已排满”当作“固件无剩余空间”。

建议：保留静态组合和既有缓存所有权；小型强类型效果结构优先于动态事件框架。记录 Flash、.data/.bss、内部 RAM、PSRAM 高水位、最大连续空闲块、栈水位、帧耗时和静态页传屏次数。结构性变更不增加素材包或改变分区。

## 4. AmoledApp 拆分设计

### 4.1 目标模块与状态归属

| 模块 | 拥有的状态与职责 | 边界 |
| --- | --- | --- |
| AmoledApp | 启动装配、主循环编排、全局游戏数据的生命周期 | 不再直接修改各页面私有字段；保留既有公共入口供板级/Web 调用 |
| InputRouter / NavigationCoordinator | 当前手势目标、输入消费、语义导航与页面生命周期 | 路由到活动流程；全局遮罩/锁屏优先；不把所有按钮逻辑搬成另一个大 switch |
| 现有五个 Controller | 各页面交互、短期状态、ViewModel | 收回可写 state；继续不依赖 App、硬件、存储和缓存 |
| ProgressionFlow | 升级/进化/学招式队列、返回上下文、反馈确认 | 数值调用现有共享服务；从所有经验来源进入同一成长流程 |
| BattleSession + BattleTimeline | 战斗阶段、回合计划、换人/胜负流程；动画/日志/音效节拍 | 复用 BattleTurnController 和 BattleActionService；明确结算与效果消费一次性 |
| ExploreSession + ExplorePresenter | 探索会话、路线暂停/结束、出发返回；预览/相机/脏区表现 | 地图算法、PRNG 顺序、资源格式继续共用 |
| HomeFlow + HomePresenter | 房间应用流程、表现状态与模型构建 | 不重写 Home::Simulation；通用资源仲裁/行为仍归共享模拟 |
| VisitFlow / PairFlow / DepartureFlow | 访客会话、伙伴交互、门口进出各自的子流程状态 | 作为 HomeFlow 的明确协作者，防止 HomeFlow 再膨胀为大类 |
| SaveCoordinator + SnapshotBuilder | 调度与重试；从当前状态生成可持久化快照 | 复用已有 coordinator；存储只走 SaveManager，保留访客剔除和 activeSlot 规范化 |
| 页面 Renderers + RenderCaches | 只读模型转像素；缓存生命周期 | 不结算奖励、不改 GameState；呈现确认显式返回所属流程 |

这些是责任边界，不要求每行都创建新类。可以先迁移一个完整子流程，再按实测复杂度决定是否细分。

### 4.2 调用与数据原则

```text
输入 -> InputRouter -> 页面 Controller / 领域 Flow
                                |
                                +-> 现有 src/game 服务 -> 唯一 GameState
                                +-> 有界 Effects -> 导航 / 保存 / 音频 / 脏区
Flow -> 只读 ViewModel -> Renderer -> 呈现确认 -> 所属 Flow
```

- GameState 只有一份权威实例；Flow 借用所需引用，自己只拥有暂态，不拷贝一整份世界。
- 不给模块传回 AmoledApp&，不引入带全部成员的 AppContext，不通过 friend 恢复原来的访问能力。
- 模块构造/操作只拿所需依赖；页面 Controller 保持纯交互，应用 Flow 调用共享玩法服务并报告硬件副作用。
- Effects 按领域定义、固定容量、明确消费/确认；奖励触发与动画反馈分开，避免重入后重复发奖。
- 时间和随机数可注入。音频可能阻塞，后续更新时间仍需正确采样；保留 uint32_t 时间回绕语义。
- 优先静态组合，先不使用通用事件总线、全局服务定位器或大规模继承树。
- 快照规范化只能操作快照/明确的视图状态，不能为保存而破坏正在运行的战斗或房间状态。

### 4.3 可维护性目标

拆分完成后，AmoledApp.cpp 可将约 1,500–2,500 行、头文件约 250 行作为复查目标；普通模块超过约 1,500 行时重新检查职责。它们不是强制切文件门槛，更不是正确性证据。优先标准是修改某一流程时，不必同时理解其他流程的私有状态。

## 5. 推荐实施顺序

| 阶段 | 可独立审查的交付 | 为什么在此阶段 | 验收重点 |
| --- | --- | --- | --- |
| 0 | 固定当前工作区基线；记录输入/更新/呈现契约；调整位置绑定测试 | 当前有大量开发中改动，先保证可比较、可回退 | 现有行为、存档与画面基线；不丢失未提交内容 |
| 1 | AMOLED 接入已有 SaveCoordinator，补失败注入测试 | 收益明确，可独立于大拆分完成 | 失败仍 dirty；受控重试；关键提交失败不推进完成态 |
| 2 | 收口 Team/Inventory/Hatch/Shower 可写状态；逐页接入生命周期；抽 ProgressionFlow | 小边界建立范式；成长被多条流程共用 | 取消/返回/锁屏、孵化保存失败、洗澡奖励与成长返回 |
| 3 | 抽 BattleSession，再分离 Timeline | 边界比房间清晰，能显著减少 App 状态 | 换人不改永久队序；音画节拍；胜负奖励只结算一次 |
| 4 | 抽 ExploreSession 与 Presenter，接入导航路由 | 先稳定战斗/成长接口，避免循环依赖 | 暂停恢复、出发/回家、探索菜单、地图指纹与 PRNG 一致 |
| 5 | 抽 HomeFlow，再逐个移出访客、伙伴与门口子流程 | 房间耦合最深，最后处理，避免一次移动数千行 | 主宠/伙伴/访客争用、进出门、休息、存取档、照料经验 |
| 6 | 页面 .inc 改独立编译单元；提取板级公共循环；最后中性目录迁移 | 逻辑边界稳定后再做物理整理 | V1/V2/Web/native 清单一致；板级差异保留 |
| 后续 | 按同样原则收口 MainScene / ExploreScene / GameEngine | 防止只清理 AMOLED，另一套继续积累 | 同一业务操作得到等价 GameState 结果 |
| Claw 恢复迭代时 | 修正 BrainBridge 槽状态、超时结果与调用幂等语义 | 专项延期，与主线拆分解耦 | 延迟消费、执行中超时、槽复用、同 ID 重试与不同 ID 合法重复 |

每阶段分成小提交：先建立行为保护，再迁移状态/方法，最后删除旧入口。不要在一次提交中同时改玩法参数、布局、存档格式和类结构。每个迁出的模块仍可通过原 App 公共入口运行，保持逐步替换能力。

## 6. 验收标准

1. 结构性步骤：固定输入、时间、随机数和初始存档时，GameState、导航结果和事件顺序一致。R1 的可靠性修复允许有明确记录的行为改善；R2 专项修复延期。
2. 输入：取消、跨按钮释放、切页后释放、锁屏与 Web 失焦都不能合成点击或重复交易。
3. 保存：失败注入覆盖“快照失败/历史失败/孵化提交失败”；成功前保留待保存状态，不覆盖高版本存档。v1–v5 兼容与显式编码继续通过测试。
4. 呈现：关键页面全帧与局部帧结果相同；静止页面不持续全刷；淡变、战斗音效和传屏确认顺序正确。
5. 玩法：访客不作为永久成员存档；战斗临时换人不改队序；照料奖励、成长事件与结算均不重复。
6. 边界：页面模块不包含 App/SDK/存储；玩法无 SDK 依赖；新增源码只加入现有权威 manifests。
