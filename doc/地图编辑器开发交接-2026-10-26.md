# StickMon 地图编辑器开发交接

交接日期：2026-10-26。本文交付开发背景、现状、约束和建议实施顺序；地图编辑器尚未实现。

## 1. 目标与用户反馈

用户希望在节日期间，让探索场景中的某个地方变成节日场景，例如小集市、小摊位。此前制作了三张原素材集市草案，用户明确反馈“不够好看”，随后要求制作本交接文档，准备开发地图编辑器。

当前目标是让用户能直接挑选素材、搭建地图、调整细节并检查实际游戏效果。编辑器应服务于通用探索地图，节日集市是第一个使用场景。

已明确的要求：

- 使用项目原素材，或从用户指定的 Pokemon Essentials Graphics 中查找；不使用 AI 生成、补画、重绘或擅自改色的美术。
- 需要可视化编排，能够人工控制构图、道路、树木、摊位和装饰。
- 必须考虑拼接、路线、出入口、角色脚底、遮挡和图层，不能只导出一张看起来成立的图片。
- 本次只生成交接文档。用户尚未要求在本轮实现编辑器，也没有批准把集市写入正式游戏。

未确认的建议：节日日期、出现位置、摊位交易、恢复 HP、奖励次数、场景数量和具体界面技术选型。上一轮建议的 A/B/C 集市布局及这些玩法不能当作已批准需求。

视觉问题的初步判断：旧草案摊位重复、按行摆放明显，大片草地缺少环境围合；道具与树林、溪流之间没有形成完整的场所关系，节日辨识度也不足。这是交接者对草案的分析，不是用户逐条提出的要求。编辑器应让这些问题可以直接修改，而不是把旧草案固化成模板。

## 3. 现有运行时的真实约束

### 3.1 尺寸、坐标与图层

| 项目 | 当前值／行为 |
| --- | --- |
| 单张探索地图 | 16 列 × 12 行 |
| 原图块 | 通常 32 × 32 像素 |
| 原像素全图 | 512 × 384 像素 |
| 逻辑世界图块 | 26 × 26 像素 |
| 逻辑全图 | 416 × 312 像素 |
| 固件地图图层 | 3 层，每层 192 个 `uint16_t` tile ID |
| 当前算法版本 | 25 |
| 边方向枚举 | 上 0、右 1、下 2、左 3 |

图层大致承担地面、物体、前景组合，但“更高的层”不等于“永远盖住角色”。现有绘制器会根据脚底与物体落地位置，在角色范围内恢复遮挡。

编辑坐标建议以格为主；提供原像素和逻辑像素读数。设备放大和相机裁切属于预览，不应改变保存的地图坐标。不能把 512×384 的原图坐标直接写进 26 像素世界路线。

### 3.2 路线和地图连接

- 每张 `Map` 有一个入口、最多 3 条完整路径；每条最多 48 个点。常量 `PATH_COUNT=2` 是历史默认，不能误认为所有地图只能两条路线。
- 普通户外路径配合双格道路使用；`cellCentered=true` 的洞穴路线使用格心。两者由 `ExploreRouteGeometry::pathPoint` 转换，不能统一按图片中心摆角色。
- 当前探索以预设路线自动行进和分路为主，并非任意点地面自由寻路。画了支路、画了可走地面，不代表角色会自动走进去。
- 地图同时包含入口、首分岔 `junction`、路径出口及结束／内部转场等字段。出口位置和方向都属于玩法数据。
- 古瀑谷正式流程使用 `generateValleyRegion`，含跨图连接和内部洞口。只调用兼容接口 `generate(seed, edge, 5)` 会得到保留的旧四洞穴，不等于当前完整区域。
- 边界出口与洞口／楼梯原地转场是不同类型。跨图还需核对目标入口、方向、通道位置、高程及路径是否终结。
- 复杂任意路网可能无法直接表示成当前“一个入口、最多三条路径”的结构。编辑器必须报告容量或拓扑不兼容，不能静默截断、伪造出口或偷偷改玩法。

| --- | --- | --- |

## 4. 素材库存与编号陷阱

### 4.1 来源与编号

同一个整数在不同 tileset 上表示不同素材。编辑数据必须保存“来源 + 源图块 ID”，或者保存有明确来源的稳定素材键，不能只保存 `515` 等裸数字。

常规图块在当前 8 列 tileset 中的关系：

```text
源图块 ID = 384 + 行号 × 8 + 列号
原像素矩形 = (列号 × 32, 行号 × 32, 32, 32)
```

这只适用于常规图块。RPG Maker XP autotile、小于 384 的槽位引用、四分块组合和 Characters 帧裁取使用其他解释方式。`Graphics/Tilesets/Outside.png` 高达 16064 像素，不能只展示顶部几排。

源图块 ID、运行时别名、`GameAssets::Kind` 和 pack 帧索引是四个不同概念。例如古瀑谷有 `9000+` 语义别名，雾林径有 `10000+` 别名；它们不是源图片上的行号，也不能直接用作 Kind。

同样像素可以有不同遮挡／通行语义；同样语义可以复用已有图像帧。去重图片时不能丢失语义。

## 5. 编辑器建议范围与交互

建议新建独立的 `tools/map_editor/`。先做本地浏览器编辑器，使用轻量本地服务读取项目和原素材；可借鉴房间编辑器的相机、素材加载、撤销和导入导出，但不要把房间多边形／家具模型硬套成探索地图模型。技术栈尚未由用户指定。

建议工作台：

- 左侧为原素材和完整组合物件库，可按树木、草、道路、水、岩壁、洞口、摊位、桌椅、人物分类，也可切换原 tileset、搜索来源与 ID。
- 中间为可缩放、平移的地图画布，像素清晰；支持矩形多格取样、吸管、笔刷、擦除、填充、框选、复制和拖动。
- 右侧为选中物件的坐标、朝向、落地锚点、占地、图层、通行和遮挡属性。
- 图层、路线、出入口、占地和深度辅助线可独立显示／锁定，预览时可全部隐藏。
- 提供“保存工程”“导出预览”“校验”“导出游戏数据”，明确区分编辑草稿、生成结果和正式项目写入。

优先做完整物件放置。例如选“一棵树”后整体移动树冠、树干、树根；选“摊位”后统一移动棚、桌、陈列和商贩锚点，仍允许进入物件内部调整。原 tileset 单格绘制作为精细编辑入口。

必须具备撤销／重做、未保存提示、错误导入不破坏现有内容、可重新打开的工程文件。仅浏览器缓存不能作为唯一保存方式。

建议先实现格子地图和整数格物件；自由像素偏移、任意深度和任意碰撞多边形是否能导入固件，需先验证表达能力。不能让界面提供一个运行时完全不支持的属性却正常导出。

## 6. 建议数据模型与接入边界

以下是新编辑器的设计建议，不是现有格式，也不是已经接通的接口。

| 数据 | 至少需要的信息 |
| --- | --- |
| 工程 | 格式版本、项目名、地图列表、素材根映射、来源校验信息 |
| 地图 | 稳定 ID、16×12 尺寸、地区／用途、三层地形、原始导入上下文 |
| 素材引用 | sourceKey、源图块或裁取矩形、动画帧／周期、允许的原图变换 |
| 组合物件 | prefab ID、组成块、局部图层、占地、共同落地锚点、遮挡类型 |
| 物件实例 | 稳定 ID、prefab 引用、地图位置、受支持的局部覆盖 |
| 路线 | 点列、格心／双格道路模式、首分路位置、入口和路径出口 |
| 连接 | 边界／原地转场类型、目标地图与目标入口、终结／内部换层语义 |
| 语义 | 地面／水／草／桥／楼梯／高程等标记及其来源；导出时映射现有实现 |
| 事件锚点 | 角色站位、互动接近点、交互朝向、事件类型预留 |
| 随机配方 | 明确的候选对象、可变区域、固定路线／出口和 seed；后续阶段实现 |

重要约定：

1. 可编辑源数据是权威来源；C++ 头文件和 pack 是生成产物，不作为编辑器保存工程的格式。
2. 保留物件实例信息，并定义实例与原始图层之间的覆盖顺序；同一次修改不能一份写实例、一份写图层而互相冲突。
3. 导入生成地图时记录 seed、入口方向、地区及段号／总段数。快照编辑和修改随机生成规则是两种操作，必须明确标记。
4. 碰撞、栖息和遮挡并非目前已存在的通用可编辑遮罩。编辑器可有语义标注，但导出器必须说明如何转换到现有 tile 规则；不支持的语义应报错。
5. 事件锚点可先作为编辑元数据。画上 NPC 或设置一个摊位 ID，不代表固件已经支持人物活动、交易或对话。
6. 第一版不需要把所有旧布局立即迁移成一种新格式。先用适配器导入和导出，保留原维护源及行为，再逐步统一。

建议数据流：

```text
Essentials 原素材 + 现有布局／生成快照
                    ↓ 导入适配器
             编辑工程 JSON / 组合物件库
                    ↓ 校验与统一编译
     Python 预览数据 + C++ 布局表 + 素材需求清单
                    ↓ 既有 GameAssets 资源管线
          正式 maps.smonfx + 固件运行时预览
```

PNG 是预览证据，不是正式游戏地图的唯一交付。保持 runtime tile atlas，不恢复整张地图位图缓存。

## 7. 必须继承的地图规则

### 构图与植被

- 道路先保证可走，再摆物件和装饰。花、树根、摊位桌腿不能盖住主路线或出入口；树冠允许覆盖部分道路。
- 普通草每片 4～9 格、鲜花每片 3～6 格、长草每片 3～5 株；完整连片、紧凑不规则，同类片区留间隔。空间不足时减少整片，不能自动退回散点。
- 长草一株两格：上格 Layer 1=`391`，下格 Layer 0=`399`。移动、复制、删除和边缘校验应按整株处理。
- 完整树木保留树冠、树干和树根；不能随意用顶部森林截片代替地图内部的完整树。详见生成规则的“顶部森林片段”。
- 透明花、树冠、水岸下面要有正确底图，避免黑洞；避免遮棚与物品被拆成无底色碎块。

### 脚底、遮挡与桥

- 角色按素材脚底／影子锚点落到路线，不能按图片中心判断前后关系。
- 同一棵树或同一物体的多个片段共享落地深度，不能按每块图片下边缘独立排序。
- 上行梯子的两格是有条件遮挡：现有别名 `4772`（Layer 2）和 `4773`（Layer 1）使用同一个下端落点；不能把上半格设成永远前景。
- 桥上角色与桥下鱼类使用不同遮挡顺序。水面环境精灵沿用鱼类白名单，不能仅凭水属性放入河中。
- 通用新物件（例如遮棚）还需要明确映射到运行时遮挡规则；编辑器临时 Z 排序不能冒充已经兼容游戏。

### 河谷、瀑布、楼梯和洞口

- 已确认峡谷画面左岸使用 `Caves:590`，右岸使用 `588`，放 Layer 1，Layer 0 保留 Caves 洞穴地面 `610`。不能交换、镜像或改为水面衬底；`Outside:1136/1138` 是另一种细水岸。
- 瀑布保留上游、瀑顶、瀑身、泡沫与下游水域关系；承接潭覆盖泡沫行及两侧，泡沫下一行保持开放水面，不得有横向干岸截断落水。
- 水面八帧、瀑布四帧，动画语义不能在导出时丢失。XP 四分块组合应复用现有算法，不能用普通九宫格规则替代。
- 洞口、向上两格梯和向下梯口是不同组合模板；根据方向和周围岩壁选型，不能只放一张门洞图片。具体取块以当前 Caves 语义及正式布局为准。
- 高桥保持 A 下层 → B 登高 → A 上层 → C 下行的现有结构；同图不同层的节点不能错误合并。内部换图不额外计探索段，结束由路径 terminal 语义决定。

## 8. 预览与自动校验

第一版至少提供三种预览：

1. 原图块全图，检查拼接和构图。
2. 26 像素逻辑图，检查缩小后的道路宽度和细节。
3. 放置可移动精灵的前后遮挡预览，显示脚底、占地和路线，并能隐藏辅助线。

设备预览后续接 StickS3、OSTB、AMOLED 的实际相机、裁切与 HUD。全图适配窗口不是实机效果；浏览器的近似绘制也不能标记为与固件逐像素一致。需要利用正式 C++ 绘制器和资源包导出帧做最终对照。

| 校验 | 失败时应指出什么 |
| --- | --- |
| 来源与范围 | 缺失文件、非法裁取、占位红叉、未知 tile／alias |
| 结构 | 越界、图层长度错误、不完整组合、空底透明块 |
| 路线 | 不连续、穿水／崖／树根、容量超过 3 条或 48 点、与道路宽度不符 |
| 出入口 | 缺少目标、方向不符、相邻通道位置不符、洞口错误出屏 |
| 物体 | 共同锚点不一致、占地与道路相交、运行时不支持的深度 |
| 水与高程 | 瀑布断流、承接潭被堵、桥无两端落点、楼梯接不上平台 |
| 导出 | 资源编号冲突、超包限制、Python／C++ 指纹不同 |

界面应高亮问题格／物件并说明原因。草稿允许保存；正式导出对不可运行的错误应阻止，并保留用户原编辑内容。

## 10. 建议实施顺序与验收

| 阶段 | 交付 | 可核对的验收点 |
| --- | --- | --- |
| P0 看得见、改得动、存得住 | 本地编辑器、素材浏览、16×12 三层、笔刷／框选／吸管、完整组合放置、撤销、工程保存／重载、PNG | 导入一张现有地图可还原；人工搭出的新地图重开后不丢物件、来源或层次 |
| P1 能正确进入游戏 | 路线／出入口／锚点编辑、语义校验、统一编译、Python/C++ 对照、正式资源预览 | 一张人工编辑地图在双方三层、路线和指纹一致，角色过树、棚、梯时正确遮挡 |
| P2 编辑地图组与有限随机配方 | 多图连接、四向入口适配、固定与可变区域、种子预览 | 相邻地图端口对齐，重入不重抽，随机物件不破坏路线与高程 |
| P3 节日场景接入 | 活动条件、场景替换、人物／互动、奖励状态 | 用户确认美术和玩法后接入；不会在半次行程突然换图、重复发奖或截断 Boss／桥洞流程 |

建议先用一张用户人工编辑的林间集市验证 P0/P1。先验证物件好摆、局部好改、遮挡可看，再扩展自动生成；不要以“自动生成大量相似预览”代替编辑体验。

第一版成功的关键是：用户能把不满意的摊位移走、重组树木与道路、调整空地和层次，并看见可信结果。无需第一版同时实现完整地区生成、全部节日和交易系统。

## 11. 节日机制的待办边界

当前共享 `GameClockService` 主要维护可加速的累计游戏分钟，不能直接当作真实公历日期。按现实节日触发需要补充可信日期来源／校时；农历节日需有年度日期配置或明确的换算方案。以上尚未实现，也没有敲定具体日期。

编辑器先保存活动／互动锚点即可。将来写入领取记录、活动状态等 GameState 字段时，须单独按存档兼容规范评估 schema、编码和迁移；不能为节日方便直接改变 struct 后忽略旧档。

上一轮“每次探险最多一次”“青草径第二段”“交易／休息／赠礼”等只是建议。后续开发需要结合用户最终选定的地图和互动方式决定，不能默认全部执行。
