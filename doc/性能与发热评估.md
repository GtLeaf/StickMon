# StickMon 场景切换性能与发热评估

> 评估日期：2026-07-28。基于代码静态分析，所有结论附 `文件:行号` 引用；实机毫秒级数据可用现有串口打点日志采集（见文末「验证手段」）。

## 结论概览

**场景切换本身不重，发热主因不在切换，而在常态渲染路径。** 代码层面没有失控的功耗黑洞，但存在几个明确的、持续性的热量来源，优化空间实在。

## 一、帧预算背景

- 主循环有帧率限制：`FRAME_MS = 66`（约 15fps），idle 时 `IDLE_FRAME_MS = 250`（约 4fps），见 `src/core/GameEngine.h:275-277`；无事可做时 `delay(1)` 让出 IDLE 任务（`src/core/GameEngine.cpp:274`）。
- 每帧 `update()`：CryPlayer 轮询、精灵缓存同步（签名未变时 early-return，可忽略）、场景 update、存档节流（`GameEngine.cpp:1544-1577`）。
- 每帧 `render()`：场景绘制后**无条件** `Hal::flush()`（`GameEngine.cpp:1611-1623`）。

## 二、场景切换开销（实际很轻）

切换采用 300ms 淡出 + 500ms 黑屏（`GameEngine.cpp:45,1581-1586`），真正的 `switchScene` 发生在黑屏期间，因此加载耗时表现为「黑屏略长」，不会表现为掉帧。

各场景 `onEnter` 开销实测：

| 场景 | onEnter 位置 | IO/解压 |
|---|---|---|
| MainScene | `MainScene.cpp:606-667` | 无重活（精灵已在 team cache 常驻） |
| MenuScene | `MenuScene.cpp:382-433` | 零 IO |
| ShopScene | `ShopScene.cpp:103-111` | 零 IO |
| ShowerScene | `ShowerScene.cpp:81-100` | 零 IO |
| SettingsScene | `SettingsScene.cpp:12-22` | 零 IO |
| HatchScene | `HatchScene.cpp:38-50` | 一次小存档读取，可忽略 |
| **ExploreScene** | `ExploreScene.cpp:997-1034` | **唯一重场景**：`loadAreaPreview()`（`ExploreScene.cpp:3125-3156`） |

ExploreScene 的开销细节：

- `loadAreaPreview()` 最多同步加载 6 个物种包（实测每个压缩 4.3~25.8KB、解压 13.5~44.2KB），LittleFS 读 + deflate 流式解压（`PokemonSprites.cpp:349-362`）。
- **选区界面每翻一个区域都全量重载 6 只**（`ExploreScene.cpp:1186` → `PokemonSprites.cpp:567-570` 无条件清空动态槽），即使池子没变。
- 出征时地图生成（`ExploreMapGenerator::generate`）为 16×12×3 = 576 个 uint16 cell 的纯 CPU 计算，亚毫秒级，可忽略。

GameAssets 四个资源包 boot 后常驻 PSRAM，无任何释放路径，场景切换不重复加载：

| pack | 帧数 | 压缩 | 解压后 |
|---|---|---|---|
| ui.smonfx | 35 | 14.2 KB | 32.1 KB |
| battle.smonfx | 48 | 13.6 KB | 96.5 KB |
| maps.smonfx | 167 | 14.9 KB | 61.1 KB |
| hatch.smonfx | 1 | 0.3 KB | 0.5 KB |

**例外**：`drawBackgroundViewport`（`GameAssets.cpp:350-365`）的全局背景缓冲只有一份（`GameAssets.cpp:81`），菜单/探索等使用不同背景的场景间往返时，整图 RLE 解码（240×135）每次都重做。

## 三、发热的真正来源（按贡献排序）

### 1. 每帧全屏 SPI 推送（最大头）

- `Hal::flush()` 无条件把 64,800 B（240×135×2）的 PSRAM canvas 推给 LCD（`Hal.cpp:63-65`）。
- SPI 40MHz（M5GFX 对 StickS3 的默认配置），理论 ~13ms/帧；`Bus_SPI::wait()` 是**寄存器级 busy-spin**（`.pio/libdeps/m5stick-s3/M5GFX/src/m5gfx/Bus_SPI.cpp:332-336`）。
- 15fps 下 CPU 每帧约 13ms 在空转 + 从 PSRAM 搬数据，**画面静止也照推**。

### 2. 240MHz 满频 + 零睡眠

- 全项目无 `setCpuFrequencyMhz`，platformio.ini 未设 `f_cpu`，默认 240MHz 满频。
- 无任何 light/deep/modem sleep。WiFi 已关（`Hal.cpp:40-41`），这点没问题。
- idle 模式很浅：只降帧率到 4fps + 背光降到 16（`GameEngine.cpp:1695-1706`、`Hal.cpp:67-76`），屏幕、CPU、外设照常全开。

### 3. 背光常亮 128/255

小屏设备上 LCD 背光本身就是主要热源之一，当前无熄屏路径（PWM 调光，GPIO38）。

### 4. 次要项

- 探索行走每帧约 210 次 tile 绘制（视口 10×7 cell × 3 层，`ExploreScene.cpp:924-946`），每次 `GameAssets::drawExploreTile` 对 167 帧的 map 包做**线性扫描**（`GameAssets.cpp:224-238`），无整图缓存，每 66ms 全量重画。
- Shower/Menu 场景每帧一次 I2C 加速度计读取（`ShowerScene.cpp:131`、`MenuScene.cpp:2499`），单次几百 µs。
- CryPlayer 每次播放都完整 LittleFS 读 + inflate（压缩 5~25KB），缓冲播完即弃不复用（`CryPlayer.cpp:46-137`）——事件性尖峰，非持续热源。

## 四、优化空间（按收益/改动比排序）

| 优先级 | 优化点 | 收益 | 改动量 |
|---|---|---|---|
| 高 | 画面无变化时跳过 `flush()`（场景 render 返回 dirty 标志，或 canvas 校验和） | 砍掉大部分 SPI 流量与忙等；静态画面占 gameplay 大部分时间 | 小 |
| 高 | idle 超时真正熄屏（display off + 背光 0），唤醒恢复 | 待机热量大头 | 小 |
| 高 | 探索选区翻页改为增量加载（按物种 diff，不清全部动态槽） | 消除翻页卡顿和黑屏延长 | 中 |
| 中 | SPI 推送间隙用 `delay()` 让出 CPU（替换寄存器空转），或降 CPU 到 160MHz | 降低常态功耗 | 小（需实测显示稳定性） |
| 中 | `drawBackgroundViewport` 增加 per-kind 解码缓存（约 64KB/份 PSRAM） | 消除场景往返时整图 RLE 重解码 | 小 |
| 中 | map pack `findFrame` 建 kind→frame 索引表（167 项，O(1) 查找） | 探索行走每帧省 ~210 次 O(n) 扫描 | 小 |
| 低 | CryPlayer 保留最后一次 PCM 缓冲（≤36KB） | 叫声连播免重读解压 | 小 |
| 低 | team 签名变化时 `freeCache` 只清 team 槽，不误伤探索动态槽（`PokemonSprites.cpp:526` → `:227-242`） | 减少无辜重载 | 小 |

## 五、验证手段

代码已带齐打点日志，优化前后接串口对比即可，无需新增仪表：

- `[PokemonSprites] source=littlefs species=… read=… inflate=… total=…`（`PokemonSprites.cpp:406-409`）
- `[PokemonSprites] cache sync … ms=… psram=… free=…`（`PokemonSprites.cpp:552-557`）
- `[GameAssets] pack=… read=… inflate=… total=…`（`GameAssets.cpp:217-220`）
- `[CryPlayer] play species=… read=… inflate=…`（`CryPlayer.cpp:109-112`）
- DeflateDecoder 把 flash 读与 inflate 分开计时（`DeflateDecoder.cpp:32-50,101-103`）。

## 总体判断

目前的架构方向是对的：15fps 帧限、资源常驻 PSRAM、懒加载、黑屏掩盖切换加载。「发热有点严重」主要等于「每帧全屏推送 + 满频 + 不熄屏」三件事的物理结果，而非算法失控。

建议先做第一档两项（跳帧推送 + idle 熄屏），体感温度和耗电会有明显改善；之后再按优先级处理探索选区增量加载与推送忙等。
